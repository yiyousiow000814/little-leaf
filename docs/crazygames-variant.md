The separate CrazyGames artifact does not replace the existing Web artifact.

CrazyGames requests a save when progress is dirty and five seconds have elapsed. Pending saves, blocked storage and active dragging defer submission. A successful platform submission clears dirty state only if no newer change occurred while saving. Paused clean state does not repeatedly rewrite the same progress. Five seconds describes the game's submission cadence; it does not guarantee remote cloud confirmation. Native and ordinary Web retain their existing greater-than-fifteen-second autosave behavior.

## Isolated developer preview export

The ordinary CrazyGames command keeps the production adapter and shell byte-for-byte unchanged. To produce a separate playable developer preview, append `--developer-preview` to `ci/build_crazygames.py` with the usual `--validated-web-build` and `--output` arguments. The full existing Web gate must still have passed for that exact source commit/tree. Running the `CrazyGames` Godot preset directly does not select the developer namespace.

The flag transforms only the fresh export copy of the adapter and its embedded shell. Profile and preference keys become `little-leaf.cg.developer-preview.profile.v1` and `little-leaf.cg.developer-preview.preferences.v1`. There is no URL switch, runtime override, production-save read, migration, fallback, or reset. Preview sessions reuse their separate test progress; the original production keys remain `little-leaf.cg.profile.v1` and `little-leaf.cg.preferences.v1`. This is key isolation inside the same SDK account/game Data store, not a separate backend or separate SDK quota.

The preview page title is marked “Developer preview,” and its existing loading presentation shows “Developer preview · Separate test progress.” That notice disappears with the normal loading layer; there is no additional overlay on gameplay controls and no viewport/engine sizing change. The preview artifact also includes `DEVELOPER-PREVIEW.txt`. Its manifest `save_variant` records the selected keys and before/after hashes for the two transformed staging inputs. Both normal Web and production CrazyGames inputs remain untouched. Missing, duplicate, inconsistent, or previously transformed inputs fail closed.

Offline guard coverage runs the complete synthetic SDK suite against standalone and embedded adapters for both variants, including failed loads/writes, reload, preferences, stale revisions, account transitions, size limits, and preservation of the opposite namespace. Python tests also exercise the CLI/export plumbing with a synthetic exporter; they do not launch Godot or prove hosted SDK behavior. Real-browser preview checks must still verify the loading notice and its dismissal, actual SDK reload persistence, and account transitions using disposable test progress. These checks do not imply authenticated cross-device or remote-cloud acknowledgement.

### Save-route isolation audit

- **Startup and fallback:** The shell installs its embedded Inbox/diagnostic/authority-codec block, then replaces both public vault objects with the CrazyGames adapter before calling `__littleLeafVault.boot()`. The ordinary IndexedDB client is constructed but never booted; its legacy reader, reopen/retry, migration and transaction paths remain dormant. The replacement public `LittleLeafVault` exposes only a reload-based retry. `tests/crazygames_storage.js --embedded` executes the actual complete embedded block with IndexedDB/localStorage/sessionStorage access denied during progress/preferences operations, and verifies that retry does not invoke storage.
- **SDK state and failures:** The preview adapter's only progress/preferences operations are `getItem`/`setItem` on its two literal preview keys. Every attempted SDK operation is audited in the synthetic fixtures, including load errors, corruption, failed writes, stale revisions and account changes. Both protected production values remain byte-identical. No reset, clear, import, fallback key, URL selector or provider switch exists. Missing preview progress creates a new random profile identity; malformed existing preview progress blocks startup rather than loading another source.
- **Pending writes and caches:** SDK `record`, `revisionText`, `opening` and `busy` live only in the current page closure. `cafe_web_save.gd` initializes pending/queued flags and confirmed/in-flight payloads in memory, consumes only the selected adapter's boot JSON, and regenerates queued saves from its current model. There is no persisted pending-write loader. Tests reject an old-profile pending submission and stop an in-flight save invalidated by an account event before its write. A reload starts a new closure and loads the selected keys again.
- **Native files and preferences:** `main.gd::_load_startup` returns from its Web branch before native profile discovery or review-file loading; `_save` returns through `web_save` before native writes. `cafe_settings.gd` selects `__littleLeafPreferences` for Web load/save without falling through to native CFG files. `cafe_web_save.gd` writes SDK payloads or newly serialized model data to `/tmp/little_leaf_vault_staging.json` before reading that staging file. It is unmounted MEMFS, not a fallback save. The shell sets `GODOT_CONFIG.persistentPaths = []` before constructing Engine, and the preset disables PWA. Python source-contract tests guard these routes; no native-engine execution is claimed here.
- **Other storage and lifecycle:** Inbox localStorage contains only profile-ID-scoped read/expiry/display-clock metadata, never a progress payload or preferences. Its projection comes from the current verified SDK record; it cannot reconstruct production progress. Embedded tests check an empty preview Inbox only accesses its own profile clock and retains unrelated preferences, pending data and another profile's metadata. Save diagnostics are session-only. Hide/pagehide/close/periodic saves all route through the same live Web controller; no second persistent queue or save provider is used. Existing Inbox, lifecycle, logging and recovery suites remain passing.

The exported HTML title identifies the preview before engine startup. `main.gd` may subsequently replace the document title, and a host iframe may hide it; rely on the actual loading notice and `DEVELOPER-PREVIEW.txt`/manifest for preview identification, and describe separate test progress when delivering it. No gameplay overlay or title-watching runtime hook is added.
