# Starter-wall grid segments and unified building model

## Unified building direction (2026-10-14)

The user clarified that the default cafe is a preset assembled grid by grid on
owned grass from the same catalog objects the player can buy. Default and later
objects must share placement, replacement, removal, persistence and rendering.
Selling every installed object must leave the owned land intact, allow a complete
rebuild, and survive save/reload without resurrecting the preset. This requirement
is independent of the separate report that white flooring sometimes disappears
and reveals grass or earlier colors; the following model audit does not establish
that report's rendering cause.

The [roadmap](../roadmap.md#current-state) owns implementation and acceptance
status. This section supersedes the historical design's requirement to retain
special starter roots forever. The historical contract below remains the evidence
for existing save compatibility, payments, geometry and approved appearance.

### Verified current representation

At main `d8e2aa6d156f2cb5b5e3f2547945e1ce04f46b63`:

- Land: the included 12 by 9 footprint plus `owned_parcels` determines ownership.
  Land ownership and the installed floor are already separate.
- Floors: `floor_finishes["x,z"] = {style, paid_cost}` is one installed product
  per cell. Replacement overwrites that record; there is no floor removal command.
  Rendering retains one quad per owned finished cell over the grass. An empty
  finish is not an implicit warm-oak product.
- Walls: `built_walls` holds ordinary unit edges, while starter roots and a complete
  21-record `shell_segment_products` ledger hold included edges and removal
  tombstones. Both are editable, but selection, transactions and rendering branch
  on their origin. A removed ordinary legacy west extension may reveal an included
  dormant ninth segment under the existing compatibility contract.
- Openings: one `wall_attachments` array refers to root, ordinary-wall or two-wall
  span hosts. IDs, offsets, widths and paid values are persistent. Some historical
  openings cover three starter segments; splitting them would change identity.
- Catalog: ordinary wall brushes expose three materials. The `original` material
  appears only when repairing an existing starter segment. Selling that segment
  does not leave a generally purchasable matching original wall.
- Furniture: fresh public startup filters the historical furnished reset, moves
  one counter and deploys the included register. Essential-removal checks apply
  even when Closed. The register is additionally coupled to one deployment
  entitlement, cashier count, duty and saved service; bypassing its sale check alone
  would not make a valid reusable item.

### Target state and invariants

Use the existing model as the authority, with domain-specific installed collections
rather than a generic new entity framework:

1. Ownership remains independent and is never erased or refunded when a structure
   is sold. Grass is terrain, not a hidden installed floor product.
2. Floors remain one product per cell. Walls become one product per grid edge,
   with stable object identity, material, height and exact paid/refund history.
   Furniture keeps existing item and linked dining-set identities.
3. Openings remain one object each. Their complete aperture and ordered supporting
   wall IDs determine support; a root alias is migration information, not a second
   active wall. No duplicate edge, ghost root, implicit floor or dormant construction
   may be generated by rendering or reloading the unified format.
4. A fresh preset is only a list of catalog placements plus included payment
   provenance. Fresh initialization invokes the same constructors and complete
   physical validation as player edits. It runs once for a genuinely fresh game.
   Included cost is not permission to invent a different resale policy.
5. Closed, idle renovation can be physically valid with no furniture or finish.
   Serving/admission readiness is a separate predicate. Active guests, jobs,
   cleanup, checkout and actor safety still constrain edits. Reopening must not
   silently create missing equipment or abandon an existing commitment.
6. The included register must be removable and placeable again with exactly one
   entitlement. Preserve payroll, roster and service identity when separating its
   deployment from equipment presence; do not reset cashier progress to enable sale.
7. Default and subsequently purchased versions of a catalog product share the same
   geometry and render path. The exact accepted geometry for new walls is coordinated
   with the wall owner; old imports retain explicit compatibility placement data.

### Pure installed-edge projection

`CafeBuildingEdges.project_validated_legacy` is the read-only adapter boundary.
It consumes a snapshot already accepted by the existing legacy decoder, not raw
untrusted save input. It is not a codec, live state owner or migration activator.

- One installed record is keyed by the grid edge. Stable IDs are retained as
  `shell:west#5` or `wall:41`; those names do not select different runtime types.
  Material, height, exact paid/refund values, endpoints, physical rectangle and
  pattern origin are explicit fields. Duplicate identities or edges are rejected.
- One opening keeps its ID, full aperture, width and paid value, with the complete
  ordered list of supporting edge IDs. Removed support, gaps and half-height
  support are rejected. A wide historical aperture is not split or narrowed.
- The separate result report lists source aliases and removed/discarded source
  IDs for review. It contains no dormant wall product or compensating inventory.
  Old full ledgers remain only in the preserved source backup. This report is not
  a new persisted schema and cannot generate construction.
- The adapter allocates a temporary snapshot on explicit use, with no retained
  cache, signal, per-frame caller or file writes. Future runtime adoption must
  cache against owned model identity/revision and release the previous snapshot;
  do not run a full projection on every draw or pointer frame.

The existing shell-model suite exercises real legacy decoding, exact physical
rectangles/refunds, three-edge and ordinary spanning openings, moved origins,

## Exact paid-value and refund preservation

Naively setting nine 55-coin segments to a 27-coin refund loses value: 9 × 27 = 243, while the old whole-wall refund is floor(495 / 2) = 247. An explicit refund credit is required.

For each inherited root:

1. Preserve its exact total paid amount P
2. Allocate deterministic integer paid shares along increasing root coordinates
3. Allocate each refund as floor(cumulative paid / 2) minus floor(previous cumulative paid / 2)
4. Therefore segment paid shares sum to P and segment refund credits sum to floor(P / 2)

For P=495 across nine units, paid shares are all 55 and credits are `[27, 28, 27, 28, 27, 28, 27, 28, 27]`, totaling 247. These extra alternating coins preserve a pre-existing aggregate entitlement; they are not new awards.

Special legacy cases:

- A paid eight-unit west wall extended to nine included units keeps its value in the first eight segments. The ninth remains free with zero refund
- A retained player-built extension leaves eight active shell segments
- The current reader also accepts a nine-unit paid amount with an eight-unit active shell. Do not reject or discard that previously accepted value: prorate it deterministically over the eight active segments (61/62 paid shares for 495), with the same exact cumulative-refund rule
- Free inherited shells keep zero paid/refund value regardless of material

After a new single-segment purchase, that segment records the ordinary current unit cost and floor(unit cost / 2) as its future refund. Every neighbor's appearance, paid amount, and refund credit stays byte-for-byte unchanged. A first edit does not reallocate credits across the remaining wall. Removing or moving a retained extension also leaves the historical allocation unchanged. Validation must find one coherent historical eight- or nine-unit basis for all inherited records in each root, rather than deriving history from its current extent; ordinary purchased records can coexist with that basis. Same-style selection is a no-op. Invalid support, insufficient coins, cancellation, and failed validation cannot charge or mutate anything.

Validate complete canonical key coverage, active/inactive geometry, enumerated styles/heights, finite integer costs/credits, per-segment credit limits, and aggregate credit ≤ floor(total paid / 2). Normalize JSON numeric fields to integers on decoding. The prototype's numeric bounds are deliberately tied to the unchanged 0.1.8 prices and accepted legacy records; no economy change is proposed.

## Opening support and rendering

An opening needs every segment intersecting its complete half-open aperture interval at full height. Exact grid-boundary contacts do not claim the neighboring segment. Examples covered by tests:

- Door centered at 5.5, width 1.0: segment 5
- Legacy door centered at 5.5, width 1.5: segments 4, 5, 6
- Moved door centered at 5.0, width 0.76: segments 4, 5
- Window centered at 4.0, width 0.70: segments 3, 4

A material-only edit remains local and does not change the aperture. Lowering any supporting segment is rejected until the opening is moved or removed through the existing validated workflow. Existing player-built spanning hosts retain their existing validation.

Keep the old renderer verbatim for a homogeneous inherited root. For mixed appearances, group consecutive equal segments into runs while retaining the original root origin, normal, and world-aligned texture coordinates. Clip solid panels around the existing apertures in root coordinates. Draw end faces only at genuine exposed ends or height steps, not at every segment/run join. Segment selection/hit testing is separate from render batching.

The prototype proves root extent/thickness/ordering and homogeneous-render eligibility. It does not prove final raster equivalence: before/after native pixel captures remain a required implementation gate.
