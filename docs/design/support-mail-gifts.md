# Support mail and gifts — item 20 draft

Status: technical proposal and partial Draft implementation, integrated with merged save-polling PR #328 (2026-10-16 UTC). It is not an accepted or deployed feature. The user asked for an owner-only in-game way to look up one UID, write to that player, and send coins and items after reviewing records. Item 19's historic stove refund eligibility and amount remain separate and unknown for current level-less saves. The release gate remains all 20 requested items completed and verified before any deployment.

## Player and owner flow

The player-facing UID is a stable **12-digit ASCII decimal string** beginning with 1–9. A trusted service allocates it with a cryptographic random source and transactionally pairs a private `players/{authUid}/identity/public` record with `playerUidIndex/{publicUid}`; collisions retry, pairs are never recycled, and a broken pair fails closed. The owner UI accepts only this public UID. The private Firebase Auth UID continues to own save/mail/session paths and is resolved only on the server. The separately owned Settings PR #330 must consume the confirmed public UID, show loading/unavailable when it cannot be confirmed, and never fall back to a raw Auth UID, local hash or truncation. This Draft does not edit its Settings/bridge ownership. Guest and other identities have no public UID. An authorized owner sees Support Mail after a live capability check, enters one exact public UID, reviews a limited current-save summary with an explicit history-availability label, composes plain text and bounded attachments, previews the full recipient/content, and sends by a second action. A sent letter is not a paid grant. The existing Inbox presents new mail alongside the existing 0.1.5 paid receipt letters, with separate IDs/read markers and no 14-day expiry for unclaimed mail. Claim requires a confirmed cloud head; the existing Decorate shelf shows real unplaced Gifts stock, uses the same placement validation and consumes stock atomically with Finish. Reading never claims.

V1 excludes broadcast mail, automatic historical-refund inference, arbitrary save edits, custom products, unique register, bundled dining, and staff/land/recipes. Initial proposed items are stove, beverage, sink, counter, bin, plant, lamp, bookshelf, rug and divider. The owner must confirm this catalogue and normal post-placement resale policy before item issuance can be enabled. Draft caps are 100,000 coins per letter, 10 units per supported product and 100 unplaced units per product, plus 20 lookups, 10 previews and 5 new sends per actor per minute. These are review values, not approved economy policy.

## Authority and interruption

Only Google-authenticated accounts can use the service. A server-managed `supportAdmins/{uid}` role document supplies narrow lookup/issue capabilities; this Draft creates no real role. Every owner operation rechecks it. Production `LITTLE_LEAF_PUBLIC_UID_ENABLED` and `LITTLE_LEAF_SUPPORT_MAIL_ENABLED` both default off. The former blocks identity allocation until explicitly activated; turning the latter off stops issue/claim but leaves already protected ordinary saves available. No browser flag, client-authored receipt or local role changes authorization. No service identity, billing, live security-rule change, role or reward is provisioned by this Draft.

Issue IDs are stable across retries. Preview binds normalized content, exact public UID and profile for ten minutes. The send transaction privately resolves the public UID and creates issue, recipient mail, case key and audit once; retry with the same ID and content returns the same mail. One recipient and case key rejects accidental second awards under another ID. A send timeout means check the same issue ID. A claim transaction checks Google Auth UID, active writer/epoch, live lease, exact save revision/digest, profile, wallet and stock caps. It then creates stock, receipt, audit and a format-3 checksummed save with claim/stock watermark, or changes nothing. Its first enrollment preserves one raw pre-transition cloud record. Repeated claims return the current authoritative save head. Existing 0.1.5 receipts and pre-grid archives remain separate.

Firestore client rules deny all direct save writes once a server-owned control document exists. Subsequent saves must use the trusted protected-save operation with the exact current head and watermark. This protects against stale official tabs and old clients; it is not a fully server-simulated economy. The supported client must freeze and flush its current native snapshot before claim, then validate/install the returned head through the existing journal and model transaction controller. A local durable receipt alone does not prove cloud confirmation. A timeout, storage failure or account change must retain recovery evidence and must not make the grant spendable early. Gift placement must commit saved furniture and stock consumption together; a visible selector without this transaction is not a completed item feature.

The Draft now includes a default-hidden owner compose/preview/send surface, authenticated Inbox list and claim action, a Gifts section in the existing Decorate shelf, native gift staging/cancel/removal, browser journal intent recovery, server claim and placement transactions, public UID allocation, and protected-save routing. Pure contract, identity, adapter and synthetic Godot tests exercise these paths. Its Functions source is deliberately absent from `firebase.json`; production issuance and claims remain default-disabled. The actual exported Web was visually inspected with a disposable browser and a synthetic in-page mail fixture for Settings, owner compose, Inbox letter and Gifts shelf. That fixture cannot send/claim or validate live backend persistence. Actual exported Web with Functions/Firestore/Auth emulators and real IndexedDB has **not** passed: this environment could not download the Firestore emulator JAR (HTTP 403). No owner visual approval exists. PR #330 Settings must adopt the public-UID contract; Switch candidates still need overlap review.

## Quality gate and evidence

Purpose/authority: support case handling requested by the owner, with user-visible UID from a separate task. UI/UX and Game Feel need real desktop, portrait and short-landscape review of Settings, preview, Inbox and Decorate. Gameplay and save authority need repeated, interrupted, stale-client and recovery cases. Art, Technical Art, Audio and Living World sources are unchanged. No per-frame work is planned; mail pages are fetched on open in 20-row pages with a 60-row client cache bound, callbacks are account-scoped, and closing/account change must release references. Stock is bounded by product and server policy.

Focused contract, public-UID allocation, adapter and journal tests are in `platform/firebase/support_mail_contract.test.mjs`, `support_mail_identity.test.mjs`, `support_mail_adapter.test.mjs` and `support_mail_client.test.mjs`; the client test covers a lost gift-placement response and exact pending-operation recovery. Synthetic native Gifts/Inbox checks are in `tests/persistence/test_support_gifts.gd`. The Firestore emulator service and rules tests are `support_mail.test.mjs` and `support_mail_rules.test.mjs`; an actual emulator pass is still required. Existing cloud-save and Inbox regressions pass on synthetic fixtures. Compiled Web/real IndexedDB **backend workflow**, portrait/short-landscape visuals, full required CI and product acceptance remain pending. The inspected desktop images are evidence of pixels under a synthetic fixture only, not authorization, persistence or a paid gift.

Open decisions: initial grantable products, resale behavior, final caps, claimed-mail display retention and release version. A future review must also verify exact owner UID at provisioning time, authorize any Functions/billing/rules activation separately, and keep a compatible protected-save path during rollback.
