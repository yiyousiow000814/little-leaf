## Feature integration questions

1. **Spatial:** Does each body remain on its legal lane/corridor, with enough actual footprint clearance at a crossing, turn, doorway or merge?
2. **Causal:** Which event permits the next action—car stopped, door available, preceding person clear, admission accepted, payment committed, all original passengers boarded?
3. **Identity:** Are logical guest/member/car IDs and the resolved appearance recipe stable across every custody handoff and restoration?
4. **Behavioral:** Is the actor's destination and waiting/yielding reason understandable, with eventual progress when the obstruction clears?
5. **System:** Which single owner advances, renders, saves/restores and retires this actor, and do pause, close, Decorate and camera visibility preserve that boundary?
6. **Controlled variation:** Are pace, arrival offsets and destinations reproducible from fixed fixture inputs, without changing demand or inventing random wandering?
7. **Animation continuity:** Do position, heading, feet, held objects and visibility remain continuous through the physical transition and actual painter order?

## Time coherence and bus-event synchronization

The user requires synchronized offscreen behavior and accepted the six-scenario design understanding. The selected implementation and experience have not been validated by this audit. Door animation, dwell/frequency, persistent bus trips and real-customer conversion remain separate product decisions.

**Verified timing:** on pinned main, `ambient_road_traffic.advance` returns when `road_visible` is false, and the legacy bus loop returns when its area is invisible. `Model._tick_step` calls `Parking.advance` without a camera test. Main and Illustration both use `effective_frame_delta`; Web lifecycle hidden/pagehide disables Main processing, and resume suppresses its first delta. Blur cancels held input but does not itself suspend simulation. No offline catch-up is applied by this inspected Main path. These facts do not establish another platform or pending background-policy branch's behavior.

Proposed rules for the selected composition:

- **Offscreen:** simulation visibility and drawing visibility are separate. Interacting road, parking and bus bodies continue under one accepted model tick and the same occupancy/yield rules. Cull artwork/rig work, not one participant's logical clock. PR158 already supplies this boundary; reconcile it once before proposing a fix.
- **Pause, Decorate and recovery:** freeze the participating logical clocks and commitments together under existing gates; hiding vehicles must not delete or respawn them. **Browser background:** retain the inspected suspension/no-catch-up policy unless a separately approved background contract supersedes it. Do not count hidden wall time as traffic or service time. Native focus loss remains an input-cancellation boundary, not an invented pause rule.
- **Resume/re-entry:** discard a suspension delta, synchronize authoritative references before the first draw, and resume ordinary bounded steps. Rebuild transient animation at the current logical pose without replaying missed doorway events or advancing a second renderer clock. Camera re-entry must not regenerate cars or reset their occupancy. A changed offscreen position is legitimate elapsed movement; a one-frame old/new pose interpolation is a presentation issue to inspect.
- **Reload:** preserve validated saved parking/member/road state. PR158 deliberately recreates its unsaved bus offscreen via `reset_traffic_entry`; distinguish that documented transient lifecycle from camera re-entry. Persisting the same bus/passenger trip through reload would change the current contract and needs explicit approval.

**Bus synchronization:** PR158 `snapshot_at`, `_set_actor` and `accept_traffic_progress` share elapsed progress; traffic refusal holds that progress. This already couples vehicle dwell, doorway sequencing and departure. Its snapshot exposes approaching/stopped/departing/away, while the inspected bus painter has fixed doorway geometry: no explicit opening/closing state or duration was found.

The proposed event order is arrival accepted → stopped at berth → door available/open → alighters clear the shared doorway → boarders cross and finish → door closed → departure/merge accepted. Door crossing requires the same simulated trip's bus to be present and stopped, with the door available at its physical anchor; viewport culling is not an absent bus. A waiting or approach animation must not authorize a doorway crossing. Holding approach/merge must not let an independent passenger clock run ahead. Departure requires passenger clearance and closed doors, then existing traffic permission.

**Decisions before implementation:** confirm whether opening/closing means an instantaneous availability event using existing artwork or a visible animation with new durations; approve any dwell/frequency change, bus persistence or real-customer conversion separately. The behavior owner coordinates with the Bus Stop art and depth owners; no extra customer demand, fare, service or save semantics follow from this proposal. Review existing PR158 gates first, then add only missing synchronized-event checks.

Extend the same Car/Bus clips with one road-offscreen pan-out/back, one pause or Decorate interruption, and one background/resume checkpoint where supported. Record authoritative clocks, occupancy/commitments, trip/door availability, passenger door-crossing times and first re-entry frames. Reuse the existing partial-return reload case. Do not expand these discriminating branches into a new matrix; until captured, overlap/jump prevention and visible door continuity remain unverified.

First select one exact dependency composition with PR158's owner; main gaps are not evidence that its existing fixes must be rewritten. Audit actual callers, first-draw synchronization and restoration on that composition. Then review CarCustomerJourney and BusPassengerJourney continuous evidence before considering any additional change. Only a reproduced defect should yield a narrow owner-relative fix: occupancy/merge admission, custody/render handoff, doorway sequencing or local pedestrian spacing. Preserve original saves, prices, arrival cadence, table/service ownership, payment and cleanup timing. Changes to real customer creation, economy or save-state semantics require explicit user product approval.

The per-frame baseline is eight cars, bounded parking parties, six candidate bus slots and 32 scalar street walkers with six/eight visible ambient rigs. Existing candidate traffic performs bounded pair checks and shared substeps; reservations cache maneuver regions. Motion/portal/native nodes need one owning illustration and explicit teardown. Any later change records worst visible occupancy, retained capacity and invalidation; no new rendering framework or FPS claim is proposed.
