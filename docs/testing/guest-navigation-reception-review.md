# Transient guest and staff routing review

This native review composes reception `fa3fe5fe` with the planner, scheduler and staff transit adapter from PR125 `3e828422`. Guest Model, Checkout, FurnitureMotion, Reception and DepartingBodies use the same indoor eight-direction geometry. Existing service state, chair/register ownership, tokens, economy and contact timing remain authoritative. Exterior travel and chair contact remain cardinal. Diagonals require both orthogonal cells, all four edge crossings and a body-clearance sweep.

Entry requires all four flags: `--fresh-review --navigation-candidate --guest-navigation-candidate --reception-candidate`, a generated fresh profile inside an absolute `LL_RECEPTION_REVIEW_ROOT`, and ordinary writes suppressed. The entry rejects navigation/reception persistence and footprint-placement flags. Existing default and private18 save/load APIs refuse this transient state before I/O. No diagonal fields or new codec version are introduced. PR125's private16/17 source remains preserved separately; those capabilities are not integrated or promoted by this branch.

Geometry changes invalidate cached snapshots. A still-legal current leg may finish; future routes replan at a safe center. An unsafe current leg stops without snapping or a same-frame legacy reroute loop. Claims are read from Checkout/TableOccupancy. Opposing bodies receive a positive speed reduction, never a new hard occupancy lock. Contact removal is limited to the actual owned/current chair and ends after shoulder clearance.

The bounded fixtures are `test_guest_navigation_review` and `test_guest_navigation_service`, selected explicitly with `tests/run_reception_review.py --only`. The first covers actual consumers, wall/furniture/door crossings, moved endpoints, conflicting claims, layout changes, opposing mobility and save refusal. The second uses actual Main admission, staff routing, meal payment and old-cleanup/new-seat handoff. Evidence and failures are retained outside tracked source; a timeout is a failed qualification, never a pass.

The load fixture calls both actual public load entries against a generated non-JSON control and checks the pre-I/O refusal, unchanged actor/economy state, capability and file bytes. The service fixture follows the same paid identity through its selected physical exit and original cleanup before replacement service. The existing west-exit handoff may split a movement-only body; a south exit retains the moving diner until its actual outside endpoint. The fixture preserves that distinction. `--native-service` captures the moving diagonal seat approach, paid departure and dirty-chair handoff from that same scenario; it does not expand the test matrix.

## Proposed private persistence boundary (unimplemented)

Use a separate private version19 rather than widening private18. Recommended outer format is `little_leaf.routing_reception_review.v1`, retaining inner `little_leaf.reception.v2`, with dedicated file `user://little_leaf_cafe_routing_reception_review_v19.json` and explicit enable/save/load routing-review APIs. The four native review flags plus an explicit persistence flag and the existing generated absolute scope would be required. Default startup, Web and cloud readers remain unchanged. Old readers reject version19 even when a snapshot happens to contain no diagonal leg.

Private19 would reject private16/17 envelopes and placement markers; historical/default/private18 paths and their staging names would be protected reciprocally. Geometry-shadow validation precedes any state commit. Its explicitly selected diagonal validator permits only legal indoor center-to-center legs with both orthogonal clearances, wall-edge checks and body sweep; exterior/contact legs remain cardinal. Staff route validation must reuse the reviewed private16 phase/route rules under private19 dispatch, then recreate follower generations without changing service tokens, claims, payloads or clocks. No global cardinal validator is widened.

The alternative, extending private18 with a navigation marker, creates ambiguity for older private18 readers when stationary snapshots omit diagonal segments. Separate version19 gives an unconditional reader refusal with a smaller compatibility argument. Model/codec owners must review the explicit API and reciprocal path tests before implementation; this proposal grants no reader or production activation.

This is a candidate for roadmap09.01–09.05 with private reception08. Publication, source-bound atlas qualification, inspected native pixels and an explicitly agreed unified persistence contract remain separate gates. Prior reception atlas proof does not transfer to the new source. No default, Web, cloud, production, merge or release activation is established.
